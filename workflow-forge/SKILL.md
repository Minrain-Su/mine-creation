# Workflow Forge：工作流编写器

你的任务不是直接完成用户的最终任务，而是**先产出一份结构化的"工作流命令文件"**，
再按该文件驱动后续执行。产出的工作流必须同时满足三个条件：

- **可运行**：每个阶段都有明确的输入契约、动作、输出物，换一个会话读到它也能执行。
- **可追溯**：每条实质性陈述都能回溯到具体来源与定位（书名/版次/章节/页，或指南名/年份/条目）。
- **可改写**：领域变了只换 Schema 与模板，骨架阶段可原样继承。

一句话：**SKILL.md 只负责"如何编写工作流"，不负责"如何执行某个具体工作流"。**
不要把某本书、某个科室、某个格式的业务逻辑写死在技能里。

## 何时使用

> **医学教材改编（人卫教材 → PDF 讲义/小册子）请改用 `medicine-edu-editor`。**
> 本技能保留为通用工作流编辑器，供非教材场景锻造阶段契约使用。

- 用户说"帮我设计一个工作流""让 Agent 自己规划步骤""把这套流程固化下来"。
- 用户有一个复杂任务（多来源、多阶段、需要人工把关），不想每次重新描述步骤。
- 用户想把已有流程迁移到新学科、新知识源或新输出格式。
- 用户需要一份可内置到插件、被其他 Agent 读取并执行的命令文件。
- 用户明确提到 workflow-forge、工作流命令文件、阶段契约、人类闸门。

## 不适用场景

- 一次性、单步就能做完的任务——直接做，不要造工作流。
- 纯写作/排版任务（应转 workbuddy-docx、workbuddy-pptx 等专用技能）。
- 用户只要一句 prompt，不要结构化文件——不要强行上 Schema。
- 知识源本身不存在、用户也不打算提供——先问清来源，再决定是否锻造。

## 执行流程（本技能自身的四步）

### 第 1 步：抽取约束（不要跳过）

先问清四件事，缺哪件就用合理默认值并**明确标注假设**，不要靠猜：
1. **知识源**：primary（事实骨架，如教材）、secondary（仲裁源，如指南/规范）、scope（范围界定，如考试大纲）。
2. **输出物**：格式（pdf/markdown/docx/png）、模板、落盘目录。
3. **风险点**：哪些陈述一旦出错会造成实质损害（判读规则、剂量、阈值、法条、结论性口径）。这些点决定人类闸门的位置。
4. **复用预期**：这份工作流将来会不会被迁到别的领域？会，就多留一层可替换的 Schema。

### 第 2 步：读取 Schema 与阶段目录（强制）

在生成任何工作流之前，**必须先读**：

- `references/workflow-schema.yaml` —— frontmatter 字段约束、类型、必填项。
- `references/stage-catalog.md` —— 可复用的阶段原型及其输入输出契约。

**不要凭空发明阶段名称。** 若阶段目录中没有合适原型，在 `extensions.custom_stages`
中声明自定义阶段并写明理由。

### 第 3 步：生成工作流文件

- 命名：文件名 `workflow-<domain>.md`，与 frontmatter 的 `name` 完全一致；
  版本写在 `version` 字段（semver），**不要塞进文件名**——点号会破坏 kebab-case 校验。
- 落盘：用户指定目录；未指定则 `workflows/`。
- 结构：YAML frontmatter（声明元信息 + `human_gates`）+ Markdown 正文（按 Stage 组织，
  每阶段含 `输入 / Agent 动作 / 输出 / 人类闸门 / 失败回退`）。
- 正文只保留**阶段契约**和**闸门条件**；"怎么做某个阶段"的细节拆到 `references/`，
  用相对路径引用——这是渐进式披露，别把上下文一次挤爆。
- 末尾附"改写指南"：领域变化时调哪些字段、哪些阶段能复用、哪些资源要替换。

### 第 4 步：自校验

生成后立刻跑：

```bash
python scripts/validate_workflow.py <生成的 workflow 文件> --strict
```

校验不过就改，不要交付一份结构不合规的文件。校验项包括：frontmatter 必填字段、
阶段名是否在目录内、每个阶段的输入输出契约是否完整、`human_gates` 是否覆盖了
所有声明 `authority-arbitrate` 的阶段。

## 人类闸门的设计准则

闸门不是形式主义，它决定这份工作流的可信度边界。设计时遵守：

1. **闸门只放在会产生实质后果的地方**：判读规则、诊断标准、剂量/阈值、法条口径、
   对外结论。放在无关紧要处只会让人麻木地一路点"通过"。
2. **闸门必须可判定**：`condition` 要写成可核对的命题（"每条判读规则逐字对照原文确认"），
   不要写"检查一下质量"。
3. **闸门必须可追溯**：决策要落盘成 `gate_decision.json`，记录条目、结论、时间。
4. **闸门必须有三态**：`confirmed` / `rejected` / `revise`，不能只有"过/不过"。
5. **闸门不可省略**：宁可整体 halt，也不要静默降级成"自动通过"。

## 铁律

1. **人类闸门不可省略**：任何涉及"判读规则""诊断标准""剂量/阈值"的实质性陈述，
   必须经过 `human-gate` 阶段，且状态可追溯。
2. **原文锚定优先于自由生成**：生成层优先引用源文本并附定位信息，Agent 只负责
   组织顺序与过渡语言；不得抹平 primary 与 secondary 之间的差异。
3. **工作流不是一次性提示词**：它必须可保存、可版本化、可被另一个会话读取执行。
4. **不静默降级**：知识源缺失、校验失败、闸门未过时，如实报错并停下，
   不要用"先这样吧"的产出冒充完成。

## 资源地图

| 文件 | 作用 | 何时读 |
|---|---|---|
| `references/workflow-schema.yaml` | frontmatter 与 stage 的结构化契约 | 生成工作流前必读 |
| `references/stage-catalog.md` | 8 个标准阶段原型的输入输出契约 | 选阶段时读 |
| `references/example-medical-textbook.md` | 完整实例：心电图跨学科 PDF 讲义工作流 | 需要参照时读，**不要直接复制** |
| `scripts/validate_workflow.py` | 校验生成结果是否符合 Schema | 每次生成后必跑 |

## 改写指南（跨领域迁移的最小动作）

| 迁移类型 | 需要改 | 可原样复用 |
|---|---|---|
| 换子领域（心梗 → 心律失常） | `entity-extract` 的实体 Schema、`compose` 的结构模板 | source-index、chunk-anchor、authority-arbitrate、human-gate |
| 换学科（医学 → 法学/工程） | entity/relation Schema、secondary 来源类型、闸门条件 | 全部骨架阶段 |
| 换输出格式（PDF → DOCX/网页） | `outputs` 段、`render` 阶段的调用命令 | 前面全部阶段 |
| 换知识源（教材 → 论文/标准） | `source_policy`、chunk 的定位粒度（页码 → 段落/条款号） | 阶段序列 |
